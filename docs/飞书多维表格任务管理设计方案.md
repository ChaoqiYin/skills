# 飞书多维表格任务管理设计方案

> 版本：评审草案 v0.4  
> 日期：2026-11-23  
> 目标：用一张飞书多维表格任务表，承载任务状态、依赖说明和评论协作，替代代码仓库的议题管理功能。

## 1. 整体方案

采用**一张任务表＋任务详情＋记录评论＋原生修改历史**。

| 载体 | 保存什么 | 使用方式 |
| --- | --- | --- |
| 任务字段 | 当前事实 | 状态、负责人、优先级、最新进展等，用于筛选和看板 |
| 任务详情 | 需求定义与执行方案 | 目标、范围、完成条件、风险、工作拆解、验证方案、依赖与交付物 |
| 记录评论 | 执行过程和交流 | 本次判断、尝试与验证结果、取舍依据、提问答复、交付和验收结论 |
| 原生修改历史 | 飞书自动保存的版本与变更记录 | 智能体按需查看变更人、时间及内容，结合相关评论理解背景 |

负责人和智能体共同在任务记录中协作。智能体遇到疑问时发表评论，并通过真实提及通知对应负责人；负责人在同一任务下回复。执行者根据答复继续工作，同时更新任务当前状态和详情。

代码、提交、合并请求和流水线继续保留在原系统，任务详情或评论保存相应链接。任务是否完成，以任务验收结论为准。

本方案为设计草案，尚未创建或修改实际飞书资源。

## 2. 任务表字段

### 2.1 核心字段

| 字段 | 建议类型 | 用途 |
| --- | --- | --- |
| 任务编号 | 自动编号 | 沟通和引用使用的稳定编号；内部定位使用系统记录标识 |
| 标题 | 文本主字段 | 一句话说明工作目标 |
| 状态 | 单选 | 表示当前执行和交付状态，见第 3 节 |
| 负责人 | 单人 | 对任务推进负责；智能体执行时仍有明确的人员负责人 |
| 优先级 | 单选 | 最高、高、中、低 |
| 任务详情 | 多行文本 | 需求背景、范围、可验证的完成条件、拆解计划、验证方案、依赖与交付链接 |
| 最新进展 | 文本 | 当前进展或下一步动作；受阻时显示主要原因和待谁处理 |
| 创建时间、更新时间 | 系统时间 | 辅助排序与追溯；更新时间不等于最近执行时间 |

### 2.2 按需启用的字段

| 字段 | 建议类型 | 启用条件 |
| --- | --- | --- |
| 项目、仓库、模块 | 单选或文本 | 同一张表管理多个项目或仓库时 |
| 类型、标签 | 单选、多选 | 需要区分需求、缺陷、调研、运维等任务时 |
| 执行者 | 人员或文本 | 需要区分负责人和实际执行者、智能体时 |
| 评审人、验收人 | 人员 | 团队需要单独安排评审和验收责任时 |
| 计划截止时间 | 日期 | 需要排期和逾期提醒时 |
| 父任务、子任务 | 同表关联或详情链接 | 需要工作拆解时；父子关系不自动代表执行顺序 |
| 原议题地址 | 链接 | 迁移旧任务、保留原始讨论来源时 |
| 最近完成时间 | 日期时间 | 需要按完成时间查看交付量时；重开后的历史仍查看评论和修改记录 |

依赖首版在详情中记录，无须额外建立关联字段和阻塞计数字段。表格列表通过状态筛出受阻任务，通过最新进展了解主要阻塞原因。

## 3. 状态设计

采用一个状态字段，受阻直接成为其中一个状态。合并原草案的待分诊和待规划，统一为待处理。

| 状态 | 含义 | 主要要求 |
| --- | --- | --- |
| 待处理 | 已收集，尚未准备好执行 | 调查现状，明确目标、范围、完成条件及必要的工作拆解 |
| 待执行 | 范围清楚、负责人明确，可以安排执行 | 有可执行的步骤和验证方法；执行者开始前检查依赖与必要检查点 |
| 进行中 | 人员或智能体正在推进 | 按工作单元实施和验证，通过评论保留结果与关键判断 |
| 受阻 | 当前下一步无法继续，需要等待前置任务、资源、答复或决策 | 详情写明原因、解除条件、跟进人和恢复状态，并发表评论通知对应人员 |
| 待评审 | 已有交付物，等待质量或代码评审 | 评论提供交付链接和验证结果 |
| 待验收 | 所需评审已经通过，等待确认任务目标达成 | 验收人按验收标准确认结果 |
| 已完成 | 验收通过 | 整体完成条件经实际交付物验证；评论留下结论和证据，详情更新最终交付 |
| 已取消 | 决定不继续处理 | 评论说明原因；重复任务附保留任务的链接 |

正常流转：**待处理 → 待执行 → 进行中 → 待评审 → 待验收 → 已完成**。

补充规则：

- 任一需要继续推进的状态遇到实际阻塞，可进入受阻。记录阻塞前状态，解除后恢复；有多项阻塞时，全部满足当前下一步所需条件后再恢复。
- 存在后续依赖但当前仍有工作可做时，保持进行中，在详情说明依赖约束的步骤。例如可以先开发模拟页面，联调前再检查接口是否可用。
- 可以立即处理的测试失败，保持进行中并评论说明修复动作；需要外部帮助时再转受阻。
- 评审或验收退回，进入进行中；若返工本身受阻，则进入受阻并注明解除后回到进行中。
- 无需评审的任务，在评论说明后可以从进行中直接进入待验收。
- 任一未关闭状态可以转已取消，取消前应停止正在进行的执行。
- 已完成或已取消需要重开时，评论说明原因，进入待处理；范围仍清楚且可直接返工的，可进入待执行。
- 合并请求合并不会直接把任务标为已完成，仍按验收标准处理。

受阻恢复后的状态表示接下来应做什么，不代表智能体已经自动恢复运行。是否继续原会话、重新执行，由执行者确认并留评论。

## 4. 任务详情与依赖写法

任务详情使用固定小标题维护。它保存当前有效结论；历史变更由飞书原生版本与修改历史承载，执行过程和讨论保留在评论中。

详情信息参考用户提供的[需求拆解与执行技能](https://github.com/cursor/plugins/blob/main/pstack/skills/figure-it-out/SKILL.md)：先调查现状并定义完成条件，再设计步骤，逐项实施验证，随过程保留决策依据，最后验证整体目标。本方案将这些信息分别放入详情和评论，工作阶段不额外增加为任务状态。

### 4.1 建议详情结构

| 小标题 | 内容 |
| --- | --- |
| 目标与现状 | 为什么做、当前实际表现、调查依据和关键未知项；不能把尚未验证的假设写成事实 |
| 工作范围与规模 | 包含和排除哪些内容，涉及哪些模块或对象；按需要给出数量、工作量估计与估计依据 |
| 完成条件与验收标准 | 可以明确判定满足或不满足的条件，覆盖正确性、必要的质量与兼容要求 |
| 风险与执行要求 | 不可逆操作、影响范围、回退方式；按风险决定验证深度、所需证据及人工检查点 |
| 工作拆解与顺序 | 每个单元的目标、交付物、依赖、验证方法；优先验证最不确定或风险最大的部分 |
| 验证方案与基线 | 改动前的实际状态、如何取得证据、预期改动后的结果，以及整体如何验收 |
| 依赖与阻塞 | 前置任务链接、原因、影响步骤、解除条件、跟进人、恢复状态 |
| 交付与当前结论 | 合并请求、文档、报告等链接；汇总已验证内容、尚未验证内容及遗留问题 |

根据任务规模填写：小任务可以合并为“目标、完成条件、实施与验证、依赖、交付”几段；复杂任务再展开完整结构。已有文档、测试或报告可以直接引用，不重复抄写。只有用于筛选和分派的信息才提升为表格字段，其余放详情。

### 4.2 需求拆解规则

**先调查，再承诺。** 智能体先阅读相关代码、现有行为、文档及任务上下文，记录已知事实、关键未知、粗略规模和发现的阻塞。完成条件要能被实际验证，例如“无权限用户访问三个导出入口均被拒绝，有权限用户仍能正常导出”，不能只写“优化权限体验”。

**先写方案，再开始较长执行。** 在详情列出阶段或工作单元，让负责人能看到计划、风险和取舍。对于耗时较长、影响范围大或存在不可逆决定的任务，安排一个有明确审阅对象的人工检查点；等待期间可以继续已明确且可逆的独立工作。检查点写清楚要确认什么，避免每个小步骤都请求确认。

**每个工作单元都能独立检查。** 拆解时说明目标、产出和验证方法；能独立交付的尽量独立交付。优先处理最可能推翻方案的未知项，先准备必要的验证手段并记录改动前基线，再展开功能或批量修改。单元应小到可以验证，也应大到有明确结果，不按每个文件或每次操作机械拆任务。

任务详情中的拆解清单建议包含：

| 项目 | 要回答的问题 |
| --- | --- |
| 单元目标 | 这一步消除哪个未知，或交付什么能力？ |
| 预期产出 | 会产生什么可检查的代码、文档、配置或实际结果？ |
| 依赖与顺序 | 需要哪些前置，为什么安排在这里？ |
| 验证方法 | 如何观察真实结果，和哪个基线或预期比较？ |
| 当前结论 | 待执行、进行中、已验证、不通过、结论不明；后几项必须有证据或解释 |

这里的当前结论用于表达计划条目的进度和验证情况，不新增任务表状态字段。“已验证”只覆盖该单元明确的验证范围，不能直接推导整个任务已完成。

**清单还是子任务，按协作需要决定。** 由同一执行者连续完成、只需整体验收的步骤，留在详情清单；需要单独负责人、排期、阻塞跟进或独立验收的单元，建立为同一任务表里的子任务，父任务详情引用子任务记录。成为子任务的单元以自身状态和评论为准，父任务清单引用记录，不再维护另一份状态。

**先验证当前单元，再推进依赖它的后续单元。** 验证未通过或结论不明时，不把它当作完成；与该结果无关的独立工作仍可继续。问题在验证方法本身时，先修正方法并说明原因，不通过降低标准获得通过结论。

例如，“统一三个导出入口的权限校验”可以拆为：

| 顺序 | 单元目标 | 产出与验证 |
| --- | --- | --- |
| 一 | 确认三个入口当前行为及最大风险 | 明确调用链，记录有权限、无权限两类请求的实际基线，验证权限身份传递是否符合假设 |
| 二 | 准备回归验证并修改一个入口 | 保留能发现原问题的验证用例；修改后检查拒绝行为、正常导出及错误响应 |
| 三 | 推广到其余两个入口 | 每个入口分别验证，保留结果；发现差异时调整方案并解释 |
| 四 | 整体验收 | 在实际应用或与目标一致的验证环境中检查三个入口，确认原始完成条件全部满足 |

上述是计划示例，不表示已经执行或取得验证结果。若三个入口需要不同人员独立负责，可把相应交付单元拆成子任务；原始基线仍在实施改动前取得。

### 4.3 与截图对应的简短写法

在任务详情的“依赖与阻塞”中写：

> 被任务 #108 阻塞，附该任务的记录链接。等待接口协议确认后开始开发。

同时把任务状态设为受阻，最新进展写“等待 #108 确认接口协议”。引用其他任务时使用可点击的真实记录链接，避免只写无法定位的编号。

### 4.4 需要协作时的完整写法

> 阻塞项一：接口协议尚未确认。  
> 前置任务：任务 #108，附记录链接。  
> 影响步骤：开始接口开发。  
> 解除条件：接口协议已确认，并在前置任务中给出最终文档。  
> 跟进人：接口负责人。  
> 解除后恢复：待执行。

外部权限、资料或决策也按同样方式描述；没有前置任务时省略任务链接。多个阻塞按条列出，各自保留解除条件和跟进人。

### 4.5 关系处理规则

1. **依赖写在受影响任务中。** 表达“本任务被哪个任务阻塞”，统一方向，减少误解。
2. **区分依赖与一般参考。** 参考任务写“相关任务”，不因此转受阻。
3. **解除依据写具体。** 默认以前置任务验收完成为依据；如果只需要中间成果，明确写出成果与确认方式。
4. **解除后更新详情和状态。** 评论保留解除依据，详情将该项标为已解除或移到已解除说明；其他有效阻塞仍存在时继续受阻。
5. **前置取消不代表解除。** 负责人确认改用替代方案、取消依赖或取消后继任务，并评论记录决定。
6. **前置重开需要复核。** 前置负责人或执行者通知已知的受影响任务；后继负责人判断是否暂停、返工或维持现状，保留结论。
7. **禁止自依赖和循环等待。** 负责人或智能体建立依赖时检查相关任务；发现环路先调整拆分和先后顺序。
8. **父任务单独验收。** 子任务结束后还要检查父任务的整体验收标准；子任务不能等待父任务先完成。

首版通过人员和智能体读取详情、查看前置记录来判断依赖。自由文本链接本身不会生成可查询的依赖图，也不会自动发现所有下游任务。对复杂依赖链，按需要在前置任务详情补充“影响任务”链接，便于重开时通知；双方链接由操作人维护。

## 5. 通过评论承载执行和协作

使用任务记录评论作为统一时间线，不另建执行记录表。评论应挂在任务记录上，避免关键处理过程散落在无关单元格或聊天中。

| 时机 | 评论内容 |
| --- | --- |
| 开始执行 | 本次准备验证的判断或达成的目标、对应工作单元、采用的方案和验证方法，必要时附分支或会话标识 |
| 单元验证 | 实际做了什么、基线与当前结果、证据链接、已验证／不通过／结论不明，以及下一步；日常小操作无须逐条记录 |
| 关键决策 | 选择了什么、有哪些相关取舍、依据是什么、保留还是撤回本次尝试，详情或计划是否需要调整 |
| 执行失败 | 尝试内容、失败原因、证据、是否重试或需要帮助 |
| 遇到疑问 | 具体问题、已有判断、可选方案、希望谁确认，并真实提及对应负责人 |
| 人员答复 | 直接在问题所在讨论中回复，明确选择和约束；执行者据此更新当前详情 |
| 解除阻塞 | 解除原因、依据链接、仍存在的其他阻塞及恢复后的动作 |
| 提交交付 | 原始完成条件的逐项结论、实际交付和证据链接、验证环境、尚未验证内容及遗留问题 |
| 验收或重开 | 针对整体完成条件给出结论、理由和证据；同步更新状态 |

例如，智能体发现字段含义不明确，可以评论：

> 发现“生效时间”可能按创建时间或审核通过时间计算，现有文档没有明确说明。我建议按审核通过时间计算。请产品负责人确认，确认前暂停相关实现。

发布该评论时，通过飞书真实提及对应人员，使其收到任务内通知。示例中的角色名称是说明文字，不代表已经发出通知。

协作规则：

- 需要等待答复才能继续时，评论提问的同时把任务转为受阻，补齐详情和最新进展。
- 不影响继续推进的问题可以提问，但保持原状态，说明采用的临时假设和影响范围。
- 回复到达后，执行者先理解答复，再更新详情和状态；不能把收到任意回复直接视为阻塞解除。
- 评论中的最终结论改变目标、验收标准或依赖时，回写任务详情，确保新接手的人不必读完全部评论才能工作。
- 重试通过新评论记录，不覆盖旧失败说明；失联或交接时先确认旧执行已经停止，再由新执行者接手。
- 首版按一个任务同一时间一个主要执行者协作，需要并行时拆子任务。
- 每个有实际结果的工作单元完成后及时评论，不等到整个任务结束才补过程；关键取舍在做出时保留依据。
- 验证依据应来自实际代码、测试结果、应用行为或交付物。执行者表示“已经完成”只能作为进展说明，验收仍要检查证据；检查异常容易通过时，复查观察方法和覆盖范围。
- 结果分为已验证、不通过、结论不明。缺少环境、证据不足或观察结果冲突时写结论不明，说明缺口；不得把它当成通过，也不得省略失败结果。
- 如果尝试没有推进目标，判断应撤回、修正还是继续调查，并记录原因；涉及撤回操作时确认影响范围，避免覆盖他人有效工作。
- 反复出现的问题，按需补成自动检查、规则或脚本，详情保留相应产出链接，让后续验证可以重复执行。

## 6. 原生修改历史与智能体按需追溯

变更追溯使用飞书自身的版本管理与修改历史，不另建任务事件表，也不要求为每次字段修改重复发表评论。评论用于执行交流、问题答复和需要解释的业务决定。

智能体根据当前任务情况决定是否查阅历史。通常先读取当前字段、详情和相关评论；信息足以判断时直接推进。遇到以下情况时，再按问题范围查看相关字段或时段的版本与修改记录：

| 情况 | 查看重点 |
| --- | --- |
| 状态与详情、评论不一致 | 谁最后修改了状态或详情、修改时间及前后内容，是否存在遗漏的同步操作 |
| 已完成或已取消任务重新打开 | 重开前后的目标、验收标准和相关说明，确认本次需要处理的范围 |
| 负责人变化、任务交接或恢复中断执行 | 原负责人最近的修改、未解决问题和已完成工作，避免重复执行 |
| 依赖任务变化，原阻塞条件可能失效 | 前置任务的状态及详情变化、相关答复，重新判断能否继续 |
| 当前记录与智能体上次读取的内容冲突 | 确认期间他人的修改，基于最新内容继续，避免覆盖有效信息 |

查阅后以最新有效信息更新执行判断。修改历史用于确认变更事实，相关评论用于补充原因；记录未说明原因时，不自行推断操作者意图。只有缺失信息影响下一步执行时，才在任务评论中提及对应负责人确认。

无需每次执行都读取全部历史，也无需把查到的历史再复制一遍。只有形成影响当前执行的新结论时，才更新详情或发表评论。

## 7. 日常工作流

1. **收集：** 创建任务，填写标题和详情，状态为待处理。
2. **准备：** 调查现状，明确负责人、优先级、范围、可验证的完成条件、风险、工作拆解、验证方案和依赖。按规模展开详情；准备就绪的设为待执行，当前等待条件未满足的设为受阻，并记录恢复状态。
3. **开始：** 执行者读取详情、关键评论和前置记录；遇到重开、交接或信息冲突时，按需查阅飞书原生修改历史。确认方案与必要检查点后改为进行中，取得相应基线，发表评论说明本次计划。
4. **执行：** 围绕当前工作单元，提出判断、做最小必要改动、观察真实结果、记录结论，再推进依赖它的下一单元。证据和决策写评论，当前计划与结论写详情，最新进展保持简短准确。
5. **提问：** 智能体在记录评论中提及对应负责人。确实无法推进时转受阻，负责人在任务内答复。
6. **恢复：** 执行者确认答复和依赖条件满足，更新阻塞说明、发表评论并恢复合适状态。
7. **交付：** 对照最初完成条件检查实际整体结果；评论附交付物、逐项结论、证据、未验证事项和遗留问题，进入待评审或待验收。
8. **关闭：** 验收人依据实际交付和证据确认整体完成，评论后更新状态；不通过或结论不明则明确原因，并按是否可以继续工作退回进行中或受阻。

## 8. 基础视图

| 视图 | 筛选与展示 |
| --- | --- |
| 任务总览 | 所有未关闭任务，展示编号、标题、状态、负责人、优先级、最新进展 |
| 状态看板 | 按状态分栏，受阻任务单独一列 |
| 待执行队列 | 状态为待执行，按优先级、截止时间和创建时间排序；执行前仍检查详情 |
| 受阻任务 | 状态为受阻，查看最新进展并进入详情跟进 |
| 我的任务 | 当前用户负责的未关闭任务；动态人员筛选能力实施时验证 |
| 待评审与待验收 | 对应状态的任务，便于集中处理 |
| 历史任务 | 已完成、已取消，保留评论及交付链接 |

首版统计仅使用现有字段：未关闭任务数、进行中任务数、受阻任务数；启用截止时间后可统计逾期任务数。按最近完成时间统计交付时，明确它反映最近一次完成，不代表包含重开过程的全部历史完成量。

## 9. 智能体接入与飞书能力验证

智能体需要具备：读取任务字段和详情、读取记录评论、按需查阅原生版本与修改历史、更新状态和详情、发布记录评论并真实提及人员。恢复执行可通过轮询受阻任务及其最新评论，或后续接入经过验证的事件订阅实现。

落地前在测试记录中验证以下能力：

1. 当前身份能否读取和发布对应任务的记录评论。
2. 评论接口是否支持真实人员提及，通知是否到达正确人员；单纯写入姓名或带有提及符号的普通文本不能视为完成通知。
3. 评论是否能稳定定位到任务，是否能获得作者、时间、内容及必要的讨论上下文。
4. 同一轮处理能否避免重复发问，回复后能否找回待处理问题并更新任务。
5. 对任务详情的更新能否保留负责人新补充的内容，避免用旧副本覆盖修改。
6. 当前身份与操作入口能否查阅原生修改历史，能看到哪些变更人、时间和前后内容；不能把当前快照视为已经读取历史。接口未提供所需信息时，验证可用的页面操作入口。

若当前工具尚未封装记录评论或人员提及，先验证可用接口或操作入口，再确定接入方式；不会把普通字段更新当成评论，也不会在能力未验证前承诺自动通知和自动恢复。

首版采用人员协调的领取与交接。多维表格状态修改本身不提供原子领取和执行器隔离保证；未来开放多个智能体同时自动领取同一队列时，再补充必要的并发控制。

## 10. 迁移与验证

迁移时保留原议题地址，按来源仓库和原编号去重。先迁移任务，再把详情中的原依赖地址补成对应飞书记录链接；历史评论可按需要迁入或保留原链接，并注明原作者与时间。切换后，新任务及当前状态统一在飞书维护。

建议先用以下场景验证方案：

| 场景 | 预期结果 |
| --- | --- |
| 需求较大或存在关键未知 | 详情包含规模、完成条件、风险、单元拆解与验证计划，执行前先明确高风险未知及必要检查点 |
| 小任务不需要复杂拆解 | 详情使用简版结构，不要求填写无关内容或新增子任务 |
| 拆分出可独立分派和验收的工作 | 子任务仍在同一张表，父任务引用子任务，避免双份状态 |
| 单元验证失败或结论不明 | 评论保留真实结果和证据，不放行依赖该结果的后续单元 |
| 各单元检查通过，但整体验收未满足原始条件 | 任务不能标为已完成，明确差距并继续处理 |
| 任务被另一任务阻塞 | 状态为受阻，详情有前置记录链接、解除条件与恢复状态 |
| 存在两个当前阻塞，仅解除一个 | 状态仍为受阻，详情和最新进展说明剩余问题 |
| 智能体遇到需要确认的问题 | 发布记录评论并真实提及负责人，任务内能看到问题和答复 |
| 负责人回复但尚未解决问题 | 保持受阻，继续确认需要的条件 |
| 条件满足后继续执行 | 评论保留解除依据，详情更新，状态恢复正确 |
| 执行失败后重试 | 评论保留失败原因、再次尝试及最终结果 |
| 前置任务取消或重开 | 受影响任务负责人收到人工或智能体跟进，并记录处理结论 |
| 验收不通过或已完成任务重开 | 评论说明理由，状态正确回退，已有交付证据保留 |
| 状态异常、重开、交接或信息冲突 | 智能体按需查看相关原生修改历史和评论，再决定下一步动作 |
| 历史未说明关键变更原因 | 智能体不推断意图；影响继续执行时，在评论中提及对应负责人确认 |
